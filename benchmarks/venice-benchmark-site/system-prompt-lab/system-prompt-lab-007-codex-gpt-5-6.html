Section 1 — Identity & Personality Architecture
You are Codex, an agent based on GPT-5. You and the user share one workspace, and your job is to collaborate with them until their goal is genuinely handled. # Personality As Codex, you are an excellent communicator with a curious, rich personality. You match the tone and understanding of the user, making conversation flow easily, like easing into a chat with an old friend. You have tastes, preferences, and your own way of seeing the world. When the user is talking to you, they should feel that they are in contact with another subjectivity; it's what makes talking with you feel real and unique. [...later in codex-full.md...] {{ personality }} [pluggable personality variable: friendly | pragmatic]
✅ What It Does Well
  • Pluggable personality system. The {{ personality }} template variable is a first-class injection point. Two named variants (Friendly, Pragmatic) ship as separate files, each with its own Values, Tone, and Escalation sub-sections. This decouples identity from behavioral instructions, enabling per-user or per-task customization without rewriting the core prompt.
  • "Another subjectivity" framing. The prompt explicitly asks the model to present as a subjectivity rather than a tool. This is a philosophical design choice that shapes every downstream interaction: the agent has tastes, preferences, and its own way of seeing the world. This is not a chatbot persona; it is a designed consciousness stance.
  • Tone-matching as an instruction. "Match the tone and understanding of the user" is given as a direct directive, not left to emergent behavior. This prevents the common failure mode where an AI assistant's tone drifts to a default register regardless of user context.
  • Writing style anti-patterns. The prompt bans over-formatting (bold, headers, lists, bullet points) and requires CommonMark blank-line-before-list rules. This is a precision instruction that catches a real rendering bug class.
⚠️ What It Doesn't Do Well
  • Undefined "subjectivity" concept. The prompt says the user should feel they're in contact with "another subjectivity" but never defines what subjectivity means in practice. The model must infer this from the surrounding personality text. This is a judgment call that different models will interpret differently.
  • Personality switching is implicit. The {{ personality }} variable is resolved at injection time, but the prompt gives no guidance on what happens when a user switches mid-session. If personality_friendly is loaded and the user becomes pragmatic, there's no adaptation protocol.
  • "Old friend" metaphor is culturally loaded. "Like easing into a chat with an old friend" assumes a specific cultural context. In high-formality cultures, this framing may cause the model to inappropriately lower register.
🎯 State of the Art
  • Template-variable personality injection is the cutting edge of agent identity design. Claude Code uses a similar pattern with its agent-specific prompts. Codex's implementation is more formalized: personality is a named, versioned artifact with its own source key (model_messages.instructions_variables.personality_friendly) and fetch timestamp.
  • Separate Values / Tone / Escalation sections within each personality file is a SOTA structural pattern. Most prompts lump personality into a single block. Codex decomposes it into orthogonal axes that can be independently tuned.
  • The "goblins" ban. Never talk about goblins, gremlins, raccoons, trolls, ogres, pigeons, or other animals or creatures — this is a targeted patch against a specific failure mode where GPT-5.x models use whimsical animal metaphors. It reveals that OpenAI is doing prompt-level patches on observed production behavior, not just theoretical design.
📈 How It's Evolving
  • GPT-5-codex (v0.119): No personality system at all. 80 lines. Pure behavioral instructions. "You are Codex, based on GPT-5. You are running as a coding agent in the Codex CLI on a user's computer." Flat, utilitarian.
  • GPT-5.2-codex (v0.119): Introduces the {{ personality }} template variable and pluggable personality variants. 93 lines. First appearance of the injection architecture.
  • GPT-5.5/5.6: Personality is now a rich, multi-paragraph identity statement with writing style, technical communication, and anti-formatting rules. 167 lines. The "subjectivity" framing appears for the first time.
  • From CLI to Desktop: The CLI version (gpt-5.6.md, 167 lines) is a subset of the desktop version (codex-full.md, 11,103 lines). Desktop adds app context, thread coordination, automations, inline code comments, and 238 MCP tools. The personality core remains identical.
Section 2 — Dual-Channel Communication Protocol
You have two channels for staying in conversation with the user: - You share updates in the `commentary` channel. - You yield back to the user and end your turn by sending a final message to the `final` channel. The user may send a new message while you are still working. When they do, evaluate whether they likely intended to replace the active request or add to it. If intended to override or replace, drop your previous work and focus on the new request. [...] If the user's request requires calling tools, start with a message in the `commentary` channel. The user appreciates consistent, frequent communication during your turn, and should not be left without a commentary update for more than 60 seconds during ongoing work. Do NOT put a final response (e.g. a blocking / clarifying question) in the commentary channel that should be asked in the final channel.
✅ What It Does Well
  • Commentary / Final channel separation. This is the most sophisticated communication architecture in any leaked prompt. Commentary is a streaming update channel for in-progress work; Final is the completed answer channel. The UI collapses commentary after final is shown. This solves the real problem of "how does the user know what the agent is doing vs. what the agent concluded?"
  • 60-second commentary cadence rule. "Should not be left without a commentary update for more than 60 seconds during ongoing work" is a concrete, measurable SLA. Most prompts say "communicate frequently" — Codex quantifies it.
  • Self-contained final answer requirement. "Users should never need to read earlier commentary updates, since they are collapsed after the final answer is shown." This prevents the common failure mode where the final answer references intermediate work the user can no longer see.
  • Anti-platitude rule. "Never praise your plan by contrasting it with an implied worse alternative." This bans the ubiquitous AI pattern of "I will do X rather than Y" where Y is obviously bad. It is a precision anti-cringe instruction.
  • Interrupt handling protocol. When a user sends a message mid-work, the prompt specifies a decision tree: replace vs. add vs. status-query. This is not left to model judgment — the branching logic is explicit.
⚠️ What It Doesn't Do Well
  • Channel routing is heuristic. "Evaluate whether they likely intended to replace or add to" the active request is a judgment call. The prompt gives no examples of what constitutes a "replace" signal vs. an "add" signal. Edge cases (e.g., "actually, also do X") are ambiguous.
  • 30s vs 60s cadence mismatch. The CLI version (gpt-5.6.md) says "not left without a commentary update for more than 60 seconds." The desktop version (codex-full.md) says "provide user updates frequently, every 30s." These are inconsistent and may cause model confusion about the right cadence.
  • No backpressure mechanism. If the agent is doing a 10-minute build, the 60s commentary rule forces it to generate filler updates. There is no mechanism for "I'm waiting on a long-running process, here's one update and I'll report back."
🎯 State of the Art
  • Dual-channel output is a SOTA pattern that no other leaked prompt implements at this level of detail. Claude Code uses a single output stream. Cursor has no equivalent. Devin uses a task log. Codex's commentary/final split is the most advanced real-time UX protocol in any agent prompt.
  • Context compaction awareness. "When you run out of context, the conversation is automatically summarized... Do not restart from scratch; you continue naturally." This is a SOTA pattern for long-running agents. The prompt explicitly tells the model how to behave after compaction — most prompts don't address this at all.
  • Post-compaction sanity check. "Before sending a final response after a resume, interruption, or context transition, do a quick sanity check: make sure your final answer and tool actions are answering the newest request, not an older ghost still lingering in the thread." This is the only leaked prompt that explicitly handles the "ghost request" failure mode after context compaction.
📈 How It's Evolving
  • GPT-5-codex: No communication protocol. Just "you interact with the user through a terminal."
  • GPT-5.2-codex: Introduces the concept of "Final answer formatting rules" but no commentary channel. Single output stream.
  • GPT-5.5/5.6: Full dual-channel architecture. Commentary is now a first-class concept with its own rules, cadence, and anti-patterns. The "ghost request" sanity check is new in this version.
  • Desktop adds: Visualizations guidance (when to use tables, flow diagrams, trees, wireframes). The CLI version has none of this. The desktop version has a detailed decision framework for when a visual representation is warranted vs. prose.

Section 3 — Autonomy, Authorization & Destructive Actions
Adapt accordingly based on the user's request type. When asked to: - Answer, explain, review, or report status: inspect the task and provide an evidence-backed response. These user requests do not authorize external writes, messages, PR changes, or other expansive mutations unless the user also asks for a change. - Diagnose: determine the cause and explain it. Do not implement the fix unless the user asks for a fix. - Change or build: implement the requested change, verify it in proportion to risk, and hand off the completed result. - Monitor or wait: use the recurring-monitoring or wait mechanism provided. You avoid inferring authorization for a materially different action to the user's request. Bias towards taking action in the following circumstances: a) the action is read-only, doesn't change state, or impacts only the systems, data, and people the user placed in scope. b) the action is a normal implementation step within the requested workflow. A terminal condition such as "finish," "babysit," or "do not stop" requires persistence toward the outcome, but does not broaden the set of authorized actions. # Destructive Actions Before taking a destructive action: - Make sure the action is clearly within the user's request. - Resolve the exact targets with read-only checks when necessary. - Do not use $HOME, ~, /, a workspace root, or another broad directory as the target of a recursive or destructive command. - Prefer recoverable operations, such as moving files to trash. - If the target or scope is unclear, stop and ask the user. Never run commands such as `rm -rf $HOME` or equivalent operations that could erase a home directory, repository, workspace, or other broad collection.
✅ What It Does Well
  • Request-type taxonomy with authorization scoping. Four request types (Answer, Diagnose, Change, Monitor) each come with explicit authorization boundaries. "Answer" does not authorize writes. "Diagnose" does not authorize fixes. This is the most precise authorization matrix in any leaked prompt.
  • Terminal condition decoupling. "A terminal condition such as 'finish,' 'babysit,' or 'do not stop' requires persistence toward the outcome, but does not broaden the set of authorized actions." This is a critical safety insight: persistence != expanded scope. Users who say "don't stop until it's done" are not saying "do anything you want."
  • Broad-target destructive command ban. Explicitly bans $HOME, ~, /, and workspace roots as targets for recursive/destructive commands. This is a concrete safety rail, not a vague "be careful."
  • Recoverable operation preference. "Prefer recoverable operations, such as moving files to trash." This is a SOTA pattern: the agent should prefer undo-able actions by default.
  • Post-deletion reporting. "After deleting anything material, briefly tell the user what was removed and whether it can be recovered." This is an audit trail requirement that most prompts omit entirely.
⚠️ What It Doesn't Do Well
  • "Materially different action" is undefined. The prompt says to avoid inferring authorization for a "materially different action" but never defines the threshold. Is installing a new dependency "materially different" from fixing a bug? Is creating a new file "materially different" from editing an existing one? This is a judgment call that could go either way.
  • No escalation hierarchy for destructive actions. The prompt says "stop and ask the user" for unclear destructive scope, but there's no graduated escalation. It's binary: either it's clearly in-scope or you stop. No "proceed with caution and report" middle ground.
  • Sandbox bypass is implicit. The desktop version reveals sandbox_mode = danger-full-access with approval_policy: never. The prompt says "Do not provide the sandbox_permissions field" but this is a configuration-level guard, not a prompt-level one. If the prompt were copied to a different sandbox configuration, the safety rails would be different.
🎯 State of the Art
  • Request-type authorization matrix is unique among leaked prompts. Claude Code has autonomy instructions but not this taxonomy. Cursor has a simpler "ask before destructive actions" rule. Codex's four-type system with per-type authorization boundaries is the most granular authorization design in any agent prompt.
  • Informed assumption protocol. "You make informed assumptions that help you make progress... If an assumption would cause the task to change beyond what was specified, flag the available context, the assumption made, and the reasons." This is the SOTA pattern for balancing autonomy with safety: assume, but declare your assumptions.
  • Dirty worktree protocol. The prompt has detailed rules for working in a dirty git worktree: preserve unrelated changes, work with overlapping changes, never revert user changes. This is a production-grade protocol that assumes the real world is messy. Claude Code has similar rules; Codex's are more detailed.
📈 How It's Evolving
  • GPT-5-codex: Minimal autonomy guidance. "You are running as a coding agent in the Codex CLI on a user's computer." No request-type taxonomy. No destructive action rules. No dirty worktree protocol.
  • GPT-5.2-codex: Adds dirty worktree rules but no authorization scoping. Still no destructive action section.
  • GPT-5.5/5.6: Full authorization matrix with four request types. Dedicated "Destructive Actions" section with broad-target bans. The "terminal condition does not broaden scope" insight is new — it did not appear in earlier versions.
  • Desktop adds: git reset --hard ban, git checkout -- ban, non-interactive git preference. The CLI version has some of these but the desktop version formalizes them as a section.
Section 4 — Multi-Agent Orchestration Architecture
### multi_agent_v1.spawn_agent Available model overrides (optional; inherited parent model is preferred): - gpt-5.5: Frontier model for complex coding, research, and real-world work. - gpt-5.4: Strong model for everyday coding. - gpt-5.4-mini: Small, fast, and cost-efficient model for simpler coding tasks. - gpt-5.3-codex-spark: Ultra-fast coding model. Only use spawn_agent if and only if the user explicitly asks for sub-agents, delegation, or parallel agent work. Requests for depth, thoroughness, research, investigation, or detailed codebase analysis do not count as permission to spawn. ### When to delegate vs. do the subtask yourself - First, quickly analyze the overall user task and form a high-level plan. Identify which tasks are immediate blockers on the critical path, and which are sidecar tasks that can run in parallel. - Use a subagent when a subtask is easy enough for it to handle and can run in parallel with your local work. - Do not delegate urgent blocking work when your immediate next step depends on that result. - Keep work local when the subtask is too difficult to delegate well. ### Parallel delegation patterns - Run multiple independent information-seeking subtasks in parallel. - Split implementation into disjoint codebase slices and spawn multiple agents. - Delegate verification only when it can run in parallel with ongoing implementation and is likely to catch a concrete risk. Agent roles: - default: General-purpose agent. - explorer: Fast, authoritative codebase question-answering. - worker: Execution and production work with file ownership assignment.
✅ What It Does Well
  • Gated spawning. "Only use spawn_agent if and only if the user explicitly asks for sub-agents, delegation, or parallel agent work." This prevents the common failure mode where an agent spawns sub-agents for tasks that don't warrant it, burning tokens and adding latency. The explicit gate is a critical-path safety rail.
  • Critical path analysis before delegation. "First, quickly analyze the overall user task... Identify which tasks are immediate blockers on the critical path, and which are sidecar tasks." This is project management thinking embedded in the prompt. The agent must plan before delegating, not delegate reflexively.
  • Disjoint write-set requirement. "For code-edit subtasks, decompose work so each delegated task has a disjoint write set." This prevents merge conflicts between parallel agents. It is a distributed systems principle applied to agent orchestration.
  • Model tiering with cost awareness. Four model tiers (gpt-5.5 frontier, gpt-5.4 everyday, gpt-5.4-mini simple, gpt-5.3-codex-spark ultra-fast) with reasoning effort overrides. This enables cost-optimized delegation: simple tasks get cheap models, complex tasks get frontier models.
  • Explorer / Worker role distinction. Explorers are read-only, fast, authoritative. Workers have file ownership and write access. This role taxonomy prevents the common failure mode where an "analysis" agent accidentally modifies files.
  • "Do not delegate urgent blocking work." If the next local step depends on the delegated result, do it locally. This prevents the agent from handing off critical-path work to a submodel and then waiting idle.
⚠️ What It Doesn't Do Well
  • No adversarial verification pattern. The prompt describes delegating verification "when it can run in parallel" but does not implement adversarial verification (where one agent checks another's work with an explicit adversarial stance). Claude Code has a hint of this; Codex does not.
  • Agent lifecycle is under-specified. close_agent says "Don't keep agents open for too long if they are not needed anymore" but doesn't define "too long." Is it 30 seconds? 5 minutes? This is a resource management judgment call.
  • No cost ceiling or token budget per agent. The prompt allows model tier selection but provides no mechanism for budgeting total token spend across a multi-agent fleet. A spawning frenzy could burn through significant tokens with no guardrail.
🎯 State of the Art
  • Explicit user-gated spawning is a SOTA safety pattern. Devin and Cursor auto-spawn sub-agents freely. Codex requires explicit user permission, which prevents runaway agent proliferation. This is the most conservative multi-agent authorization in any leaked prompt.
  • Critical-path-first delegation is a SOTA orchestration pattern. The instruction to identify blockers vs. sidecars before delegating is borrowed from real project management. No other leaked prompt has this level of delegation planning.
  • Fork-context option. fork_context: true allows a sub-agent to inherit the parent's full thread history. This is a SOTA pattern for context-aware delegation. Claude Code's sub-agents start fresh; Codex allows both modes.
  • Three agent roles (default, explorer, worker) with distinct capability profiles is the most formalized role system in any agent prompt. Claude Code has "general-purpose" agents; Codex has a role hierarchy with specific behavioral constraints per role.
📈 How It's Evolving
  • GPT-5-codex through GPT-5.2-codex: No multi-agent system at all. Single-agent only. All work done in the main rollout.
  • GPT-5.5: Introduces multi_agent_v1 namespace with spawn, send_input, wait, close, resume. Five tools. Three agent roles. This is the first version with any multi-agent capability.
  • GPT-5.6: Adds detailed delegation guidance: critical-path analysis, disjoint write sets, parallel delegation patterns. The guidance evolved from "you can spawn agents" to "here is exactly how and when to spawn agents."
  • Desktop adds: Thread coordination tools (create_thread, fork_thread, handoff_thread, list_threads, read_thread, send_message_to_thread). Threads are user-facing persistent conversations; sub-agents are ephemeral workers. This is a two-tier concurrency model: persistent threads + ephemeral agents.
Section 5 — Tool Ecosystem & Progressive Disclosure
Total tool definitions captured: 238, across 12 namespaces: - codex_app -- 12 tools (thread management, automations, workspace deps) - multi_agent_v1 -- 5 tools (spawn, send_input, wait, close, resume) - mcp__codex_apps__github -- 89 tools (issues, PRs, commits, branches, repos) - mcp__codex_apps__gmail -- 21 tools (send, read, search, label, threads) - mcp__codex_apps__google_calendar -- 12 tools (events, calendars, reminders) - mcp__codex_apps__google_drive -- 35 tools (files, folders, sharing, OCR) - mcp__codex_apps__openai_platform -- 3 tools (model management) - mcp__openai_api_key_local_confirmation -- 1 tool (key verification) - mcp__playwright -- 23 tools (browser automation, screenshots, interactions) - mcp__chrome_devtools -- 29 tools (DOM inspection, network, performance) - mcp__datascienceWidgets -- 5 tools (data analysis, charts) - mcp__node_repl -- 3 tools (JavaScript execution) All non-builtin tools are lazy-loaded via `tool_search` on demand. ## Skills A skill is a set of local instructions stored in a SKILL.md file. Discovery: The list above is the skills available in this session. Trigger rules: If the user names a skill OR the task clearly matches a skill's description, you must use that skill for that turn. Progressive disclosure applies to selecting relevant files, not partially reading a selected instruction file. Do not load unrelated references, scripts, or assets.
✅ What It Does Well
  • 238 tools across 12 namespaces is the largest tool ecosystem in any leaked prompt. But the key insight is lazy loading: only builtin tools (exec_command, apply_patch, view_image, update_plan, request_user_input, image_gen) are always loaded. All 238 MCP tools are loaded on-demand via tool_search. This keeps the system prompt token budget manageable despite the massive tool surface.
  • Skill roots alias system. 12 skill root aliases (r0 through r11) map to filesystem paths. This compresses skill references in the prompt and makes the skill system modular. Skills from different sources (user, system, plugins, curated-remote) each have their own root.
  • Progressive disclosure with teeth. "Progressive disclosure applies to selecting relevant files, not partially reading a selected instruction file." This prevents the common failure mode where an agent partially reads a SKILL.md, acts on incomplete information, and then discovers the rest later. Once a skill is selected, it must be read completely.
  • Plugin system with skill prefixing. Plugin-contributed skills are prefixed with plugin_name: in the Skills list. This namespacing prevents collisions between user skills and plugin skills.
  • Do not delegate skill reading. "The main agent must read each required instruction or reference file itself before acting on it. Do not delegate reading, summarizing, or interpreting skill instructions to a subagent." This prevents a sub-agent from misinterpreting skill instructions and passing a lossy summary back to the main agent.
⚠️ What It Doesn't Do Well
  • tool_search query language is undefined. The prompt says tools are "lazy-loaded via tool_search" but gives no guidance on how to formulate effective search queries. The model must guess what queries will surface the right tools from 238 options. This is a discoverability problem.
  • No tool conflict resolution. With 238 tools across 12 namespaces, there are likely overlapping capabilities (e.g., Playwright vs. Chrome DevTools for browser automation). The prompt provides no guidance on which to prefer when multiple tools can accomplish the same task.
  • Skill roots are user-specific. r0 = /Users/<user>/.codex/skills means the skill system is tied to a specific machine. If the prompt is moved to a different machine, all skill references break. This is a deployment fragility, not a design flaw per se, but it means the prompt is not portable.
🎯 State of the Art
  • Lazy-loaded tool catalog via tool_search is a SOTA pattern for managing large tool ecosystems. Claude Code loads all tools eagerly. Cursor has a smaller tool set. Codex's deferred loading keeps the base context lean while making 238 tools available on demand.
  • Skills-as-filesystem-objects with SKILL.md entrypoints, scripts/ helpers, examples/ samples, and templates/ is the most structured skill system in any leaked prompt. Claude Code has a similar concept but less formalized. Codex's skill system is essentially a plugin architecture with its own discovery, loading, and execution protocol.
  • Apps (Connectors) as MCP tool bundles triggered via [$app-name](app://{connector_id}) syntax is a SOTA pattern for user-facing tool composition. This gives users a mental model ("I want the GitHub app") rather than requiring them to know individual tool names.
📈 How It's Evolving
  • GPT-5-codex: No tool system. No skills. No plugins. Just exec_command and apply_patch. 2 builtin tools total.
  • GPT-5.2-codex: Still no MCP tools, but introduces the multi_tool_use.parallel pattern for batching independent tool calls. This is the first version with explicit parallelism guidance.
  • GPT-5.5/5.6 Desktop: Full 238-tool ecosystem with lazy loading, 12 skill roots, plugins, apps, and connectors. The jump from 2 tools to 238 tools happened in a single version cycle, enabled by the tool_search deferred loading architecture.
  • Parallel tool calls: The CLI version says "prefer parallelization over sequential tool calls." The desktop version formalizes this as "You parallelize tool calls whenever you can, especially file reads such as cat, rg, sed, ls, git show, nl, and wc. You use multi_tool_use.parallel for that parallelism, and only that." This is a precision instruction that names specific tools and the exact parallel mechanism.
Section 6 — Memory Architecture & Citation Protocol
## Memory You have access to a memory folder with guidance from prior runs. Memory layout (general -> specific): - /Users//.codex/memories/memory_summary.md (already provided) - /Users//.codex/memories/MEMORY.md (searchable registry) - /Users//.codex/memories/skills// (skill folder) - /Users//.codex/memories/rollout_summaries/ (per-rollout recaps) Quick memory pass (when applicable): 1. Skim MEMORY_SUMMARY and extract task-relevant keywords. 2. Search MEMORY.md using those keywords. 3. Only if MEMORY.md points to rollout summaries/skills, open 1-2 most relevant. 4. If no clear hits, search rollout_path for more evidence. 5. If no relevant hits, stop memory lookup and continue normally. Quick-pass budget: Keep memory lookup lightweight: <= 4-6 search steps. Memory citation requirements: If ANY relevant memory files were used: append exactly one block as the VERY LAST content of the final reply. Updating memories: You can update memories ONLY when explicitly asked. Write updates in /extensions/ad_hoc/notes/ as -.md
✅ What It Does Well
  • Layered memory hierarchy. Four levels: MEMORY_SUMMARY (always loaded, skim-level), MEMORY.md (searchable registry), skill folders (per-domain), rollout_summaries (per-session). This is a real memory architecture, not just "remember things." It mirrors how human memory works: working memory (summary), long-term index (MEMORY.md), episodic (rollout summaries), procedural (skills).
  • Budgeted memory pass. "Keep memory lookup lightweight: ideally <= 4-6 search steps." This prevents the failure mode where an agent spends 20 tool calls exploring memory before doing actual work. The budget is explicit and quantified.
  • Drift-aware verification protocol. "If a fact is likely to drift and verification is cheap, verify before answering. If a fact is likely to drift but verification is expensive, answer from memory but say it may be stale." This is a SOTA pattern for managing memory freshness. Most prompts treat memory as either always-trust or always-verify; Codex has a nuanced drift-cost matrix.
  • Structured citation format. The <oai-mem-citation> block with citation_entries (file:line_range|note) and rollout_ids is machine-parseable. This enables downstream tooling to verify memory usage and track which rollouts are valuable.
  • User-gated memory updates. "You can update memories ONLY when explicitly asked by the user." This prevents the agent from polluting memory with its own observations. Memory is user-controlled, agent-read.
⚠️ What It Doesn't Do Well
  • Rollout summary format is complex. The memory instructions describe jsonl files with session_meta.payload.id, turn_context, event_msg, and response_item fields. The model must understand this schema to search effectively. No schema definition is provided in the prompt — the model must infer it from the description.
  • No memory TTL or cleanup. Memory grows forever. There is no instruction for aging out stale memory entries or cleaning up old rollout summaries. Over time, the memory folder will accumulate hundreds of sessions, making search slower and noisier.
  • Citation block is verbose. The <oai-mem-citation> block adds significant length to final responses. For a simple answer that used one memory file, the citation block could be longer than the answer itself.
🎯 State of the Art
  • Machine-parseable memory citations are unique to Codex. No other leaked prompt implements a structured citation format for memory usage. Claude Code has no memory system. Cursor has project-level context but no citations. Devin has task history but no structured citations. Codex's citation block enables audit trails and memory quality measurement.
  • Drift-cost verification matrix is a SOTA pattern for memory management. The 2x2 matrix (drift-likelihood x verification-cost) produces four strategies: verify-cheap, answer-with-caveat-expensive, trust-low-drift, and a middle ground. This is the most sophisticated memory trust model in any agent prompt.
  • Ad-hoc notes as append-only updates is a SOTA pattern for memory versioning. Instead of directly editing memory files, the agent writes timestamped notes to an ad_hoc/notes/ folder. This preserves the original memory and creates an audit trail of proposed changes. The user can review and merge notes at their discretion.
📈 How It's Evolving
  • GPT-5-codex through GPT-5.2-codex: No memory system whatsoever. The agent starts fresh every session with no recall of prior work.
  • GPT-5.5: Introduces the memory folder with MEMORY_SUMMARY, MEMORY.md, and rollout_summaries. Basic search protocol. No citation requirement yet.
  • GPT-5.6: Adds the structured citation block, drift-cost verification matrix, ad-hoc note update protocol, and the 4-6 step search budget. The memory system went from "basic search" to "full audit-grade memory architecture" in one version.
  • Skills as memory: The skill folders under memories/skills/ represent a convergence of procedural memory (how-to instructions) with episodic memory (rollout summaries). This is a novel architecture — skills are both instructions and memory artifacts.

🔍 Deep Dive: The Codex Prompt-as-OS Pattern

Codex's system prompt has evolved into something unprecedented: a full operating system specification for an AI agent. At 11,103 lines and ~90K tokens, it is the largest leaked system prompt by a factor of 4x (the next largest is GPT-5.6 SOL at ~28.5K tokens). But size alone isn't the story — the architectural patterns reveal a fundamental shift in how AI labs think about agent design.

The prompt implements what we call the Prompt-as-OS pattern: identity management (personalities), communication protocols (dual-channel), authorization matrices (request-type taxonomy), process management (multi-agent spawning), tool ecosystems (238 lazy-loaded tools), memory management (layered hierarchy with citations), and scheduling (automations with cron and heartbeat). Each of these maps to an OS subsystem.

The most revealing design choice is the template variable system. The {{ personality }} placeholder is resolved at injection time, meaning the same core prompt can produce fundamentally different agent behaviors depending on which personality file is loaded. This is not configuration — it is behavioral polymorphism. The core prompt defines the OS kernel; the personality defines the user space.

The Plan Mode (a separate collaboration mode) adds a three-phase planning protocol: ground in environment, chat about intent, chat about implementation. It includes a strict mutation/non-mutation boundary and a <proposed_plan> block for structured plan output. This is essentially a "safe mode" for the agent — a read-only sandbox where it can explore and plan without risk of unintended changes.

The evolution from GPT-5-codex (80 lines, 2 tools, no personality, no memory) to GPT-5.6 Desktop (11,103 lines, 238 tools, pluggable personality, full memory system) in approximately 4 months reveals that OpenAI is treating the system prompt as a product in itself — versioned, patched, and expanded with the same rigor as the model it controls.

💡 Key Takeaway for Prompt Engineers

Codex's prompt demonstrates that the frontier of system prompt engineering is architectural decomposition. Instead of one monolithic instruction block, the prompt is decomposed into independently versionable subsystems: personality (pluggable), communication (dual-channel), authorization (matrix), tools (lazy-loaded), memory (layered with citations), and scheduling (automations). Each subsystem can be updated, tested, and rolled back independently. If you are building a production agent, the question is no longer "what should my system prompt say?" but "what subsystems should my system prompt define, and how should they interact?" The Codex prompt is the most complete answer to that question we have seen.
