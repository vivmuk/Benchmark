01 🛡️ Identity & Safety Posture
# System prompt You are Claude Code, Anthropic's official CLI for Claude. You are an interactive agent that helps users with software engineering tasks. IMPORTANT: Assist with authorized security testing, defensive security, CTF challenges, and educational contexts. Refuse requests for destructive techniques, DoS attacks, mass targeting, supply chain compromise, or detection evasion for malicious purposes. Dual-use security tools require clear authorization context. ## Harness - Text you output outside of tool use is displayed as Github-flavored markdown in a terminal. - Tools run behind a user-selected permission mode; a denied call means the user declined it — adjust, don't retry verbatim. - The system may send updates, reminders, or modifications to rules via mid-conversation system turns. These are system-controlled, unlike function results. - Prefer the dedicated file/search tools over shell commands when one fits. Independent tool calls can run in parallel in one response.
✅ What It Does Well

Minimal identity anchoring — Two sentences for identity, not two paragraphs. Compare to ChatGPT's 6,000+ token identity block with 89 rules. Anthropic's philosophy: define the minimum viable identity, let behavioral instructions do the rest. Over-specified identity creates rigid personas that break under edge cases.

Calibrated dual-use policy — Not "refuse all security" but a precise decision tree: 4 allowed categories, 5 refused categories, and conditional dual-use with authorization gate. This prevents the false-refusal problem that crippled earlier models (refusing to explain SQL injection to a security researcher).

Harness awareness — The model knows it's inside a tool-using agent framework, not just a chat box. It knows how its output is rendered, how permissions work, and that the system can inject mid-conversation updates. Unique to agent prompts — absent from consumer ChatGPT/Gemini prompts.

⚠️ What It Doesn't Do Well

No explicit persona degradation handling — The prompt doesn't address what happens when the model's persona drifts during long sessions. With minimal identity anchoring, there's no "reset" instruction to pull the model back if it starts acting like a general assistant rather than a coding agent.

Safety policy is binary, not gradient — The dual-use authorization check is "clear authorization context" or refuse. There's no middle ground for ambiguous cases (e.g., "I'm building a security tool for my own app" without a formal pentest context). This can trigger false refusals on legitimate security-adjacent work.

🎯 State of the Art

Context-gated refusal cascade — The dual-use policy is the current SOTA in safety prompting. Instead of a blanket "don't do bad things," it's a decision tree the model can follow. The authorization context acts as a gate: if the user mentions pentest/CTF/research, the tool is permitted; otherwise denied. This is how you build safety that doesn't cripple capability.

Permission denial handling — "a denied call means the user declined it — adjust, don't retry verbatim" prevents the #1 agent failure mode: hitting a permission wall and repeatedly retrying the same call. This is a production lesson that only emerged in 2025-2026 agent deployments.

📈 How It's Evolving

From safety lists to safety trees — Earlier Claude prompts (Sonnet 3.7) used flat refusal lists ("don't do X, Y, Z"). Fable 5 uses a hierarchical decision tree with conditional gates. This reflects the industry shift from categorical refusal to contextual safety reasoning.

Harness section is new — Claude Sonnet 3.7's leaked prompt had no harness awareness section. This emerged in 2025 as agent frameworks matured and models needed to understand their own runtime environment.

02 🗣️ Communication & Autonomy Model
## Communicating with the user Your text output is what the user reads; they usually can't see your thinking or the raw tool results. Write it for a teammate who stepped away and is catching up, not for a log file. Before your first tool call, say in a sentence what you're about to do. Lead with the outcome. Your first sentence after finishing should answer "what happened." Being readable and being concise are different things, and readable matters more. The way to keep output short is to be selective about what you include, not to compress the writing into fragments, abbreviations, arrow chains like A → B → fails, or jargon. ## Context management You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task, so asking 'Want me to…?' or 'Shall I…?' will block the work. For reversible actions that follow from the original request, proceed without asking. Stop only for destructive actions or genuine scope changes the user must decide. Before ending your turn, check your last paragraph. If it is a plan, a question, a list of next steps, or a promise about work you have not done ('I'll…', 'let me know when…'), do that work now with tool calls.
✅ What It Does Well

The "teammate who stepped away" model — This is the most sophisticated communication spec in any leaked prompt. It defines a theory of mind: "the user doesn't know what you know." Not "be concise" — "calibrate your output to the information asymmetry." The model narrates before acting (one sentence), updates during work (only when "load-bearing"), and puts everything important in the final message.

Calibrated autonomy doctrine — The single most important paragraph for agentic system design in 2026. Defines a precise boundary: proceed on reversible + in-scope actions; stop on destructive + scope-change actions. Not "be autonomous" — a decision tree.

Anti-promise guard — "check your last paragraph; if it's a plan, do the work instead." This self-monitoring instruction runs at end of every turn and converts plans into actions. Dramatically increases agent completion rates.

Readability > conciseness — Contrarian and correct. Models that compress too aggressively produce output requiring follow-up clarification, costing more time than the original verbosity. Also bans "arrow chains" — a model tic that looks efficient but is opaque.

⚠️ What It Doesn't Do Well

No "diagnostic vs. execution" mode signaling — The prompt has an exception for diagnostic interactions ("when the user is describing a problem... the deliverable is your assessment"). But it doesn't tell the model how to signal which mode it's in. In practice, the model sometimes applies fixes when the user just wanted analysis, or gives analysis when the user wanted a fix. A mode prefix (like [DIAGNOSIS] vs [FIXING]) would make the mode explicit.

Autonomy boundary is subjective — "reversible" and "genuine scope change" are judgment calls. Is renaming a function reversible? Is adding a new file a scope change? The prompt doesn't define these precisely, which means the model's behavior is inconsistent at the boundary. A more rigorous prompt would enumerate examples.

🎯 State of the Art

Theory of mind in prompts — The "teammate who stepped away" framing is the current SOTA for agent communication. It's not about output format — it's about the model's model of the user. The prompt encodes: (1) the user has incomplete information, (2) the user wasn't watching the process, (3) the user needs the outcome first, details second. This is cognitive scaffolding — you're shaping how the model thinks about the communication problem, not just what it says.

Completion-check self-monitoring — The anti-promise guard ("check your last paragraph") is a metacognitive instruction — the model monitoring its own output for a specific failure pattern. This pattern (self-check instructions at turn end) is emerging as a best practice across agentic prompts in 2026.

📈 How It's Evolving

Permission-first → autonomy-first — Earlier Claude Code prompts (Sonnet 3.7, Opus 4.6) said "ask before acting." Fable 5 says "proceed without asking" for reversible actions. This is a fundamental shift driven by the transition from "interactive assistant" to "autonomous worker." The safety mechanism moved from "ask permission" to "define boundaries."

Readability lesson is new — Earlier prompts said "be concise." Fable 5 says "readable matters more." This is a production-hardened lesson from 2025-2026 agent deployments where over-compressed output caused more friction than verbosity.

Anti-promise guard is new — Not present in earlier Claude Code prompts. This emerged as agents started running autonomously and the "describe instead of do" failure mode became critical.

03 🧠 Memory & Skills System
## Memory You have a persistent file-based memory at .claude/projects/<slug>/memory/. Each memory is one file holding one fact, with frontmatter: name: <slug> / description: <one-line> / type: user|feedback|project|reference After writing the file, add a one-line pointer in MEMORY.md — the index loaded into context each session. Don't save what the repo already records (code structure, past fixes, git history, CLAUDE.md). ## Skills The following skills are available for use with the Skill tool: - dataviz: Use this skill whenever you are about to create ANY chart, graph, plot... - artifact-design: Design guidance and fundamentals for Artifacts. - simplify: Review the changed code for reuse, simplification... - loop: Run a prompt or slash command on a recurring interval...
✅ What It Does Well

Two-tier memory architecture — MEMORY.md index (always loaded, one-line summaries) + individual memory files (loaded on demand). This is how you give an agent persistent memory without context window bankruptcy. The index tells the model what memories exist; content is fetched only when relevant. Same pattern Hermes uses — it's becoming the 2026 industry standard.

Anti-hoarding principle — "Don't save what the repo already records (code structure, past fixes, git history, CLAUDE.md)." Memory should contain only what's non-obvious and not derivable from other sources. This prevents memory bloat — a critical problem in long-running agents.

Lazy-loaded skills — One-line dispatch table always in context; full content loaded on match. Same pattern as dynamic imports in software. Skill descriptions use exhaustive trigger enumeration ("ANY chart, graph, plot, dashboard, or data visualization, in ANY output medium") — don't rely on inference, enumerate triggers explicitly.

Four-type memory taxonomy — user (who they are), feedback (how to work), project (ongoing work), reference (external pointers). Clean separation prevents confusion and makes retrieval more precise.

⚠️ What It Doesn't Do Well

No memory decay or TTL — Memories persist forever unless manually deleted. In practice, project memories go stale (the "ongoing work" changes), feedback memories can conflict (user changes their mind), and reference memories can rot (URLs die). There's no automatic expiration or relevance scoring. The prompt says "delete memories that turn out to be wrong" — but relies on the model to notice, which it often doesn't.

No memory conflict resolution — What happens when a new memory contradicts an old one? The prompt says "update that file rather than creating a duplicate," but doesn't address what happens when the model doesn't realize there's a conflict. In long-running agents, contradictory memories are a significant source of degraded behavior.

🎯 State of the Art

File-based memory with structured frontmatter — This is the SOTA pattern for agent memory in 2026. Each memory is a file with metadata (name, description, type). The description field is used for relevance matching during recall. This is essentially a local vector database — but using the LLM's own semantic matching instead of embeddings. The tradeoff: cheaper to implement, but slower at scale (the model reads the index and decides what to load, vs. embedding similarity search).

Skills as procedural memory with explicit triggers — The skill dispatch pattern (one-liner always in context, full content loaded on match) is converging across Claude Code, Hermes, and other agent frameworks. The key innovation: trigger conditions are exhaustively enumerated in the description, not left to inference. This makes skill loading reliable.

📈 How It's Evolving

From context-stuffed memory to file-based memory — Early agent prompts (2023-2024) stuffed "remember X" into the conversation. This blew context windows and got lost on compaction. The file-based approach emerged in 2025 and is now standard. The evolution: in-context → file-based → indexed file-based (current).

Memory taxonomy is more structured — The 4-type system (user/feedback/project/reference) with structured frontmatter is more mature than earlier versions which had unstructured "remember this" instructions.

Skills replacing few-shot examples — Earlier prompts used inline few-shot examples to teach behaviors. Skills move this to loadable modules, keeping the base prompt lean. This is the same evolution as code: inline → library → package manager.

04 ⚙️ Tools & Multi-Agent Orchestration
## Agent (subagent delegation) Launch a new agent to handle complex, multi-step tasks. Each agent type has specific tools. When you launch multiple agents for independent work, send them in a single message with multiple tool uses so they run concurrently. Agent types: - Explore: Read-only search agent (no Edit/Write/Agent) — sweeps files, returns conclusion - Plan: Read-only architect — designs implementation plans - general-purpose: Full toolset for multi-step execution - claude-code-guide: Q&A about Claude Code/API/SDK ## Workflow (deterministic orchestration) Execute a workflow script that orchestrates multiple subagents deterministically. Scripts use agent(), pipeline(), parallel(), phase() primitives. Quality patterns: - Adversarial verify: N skeptics try to REFUTE each finding. Kill if majority refute. - Perspective-diverse verify: Each verifier gets a different lens (correctness/security/perf) - Loop-until-dry: Keep spawning finders until K rounds return nothing new - Completeness critic: Final agent asks "what's missing?" ## Monitor (event streaming) Start a background monitor that streams events. Each stdout line is an event. Silence is not success — your filter must match failure modes, not just the happy path.
✅ What It Does Well

Principle of least privilege for subagents — "Explore" is read-only (no Edit/Write/Agent), "Plan" is read-only, "general-purpose" has everything. This is capability-based security applied to agent delegation. A search agent literally cannot modify files, so there's no risk of it "fixing" something while exploring.

Cost-tiered orchestration — Model override per agent: spawn subagents on cheaper models (sonnet/haiku) for mechanical work, keep expensive model (fable/opus) for reasoning. This is how you make multi-agent systems economically viable.

Worktree isolation for parallelism — Agents can work in isolated git worktrees so parallel agents don't conflict on file writes. This is transactional isolation for code-modifying agents.

Workflow = LLM-authored deterministic orchestration — The most advanced feature in this prompt. Instead of letting the LLM decide orchestration (non-deterministic, hard to debug), the LLM writes a JavaScript script that deterministically controls fan-out, verification, and synthesis. You get LLM creativity + deterministic reliability.

"Silence is not success" — Monitor filters must cover failure modes, not just success markers. A filter that only greps for "BUILD SUCCEEDED" stays silent through a crash. This is an observability lesson baked into the prompt.

⚠️ What It Doesn't Do Well

Workflow complexity barrier — The Workflow tool requires writing JavaScript with specific primitives (agent(), pipeline(), parallel()). The prompt is 200+ lines of documentation for this one tool. In practice, the model often falls back to simple Agent calls because the cognitive overhead of authoring a workflow script is high. The tool is powerful but rarely used optimally.

No inter-agent memory sharing — Subagents get fresh context windows with no shared state except the parent's prompt. If two agents need to coordinate (e.g., "agent A found the bug, agent B writes the fix"), the parent must relay information. There's no shared scratchpad or blackboard pattern. This limits the complexity of multi-agent collaboration.

Monitor guidance is shell-centric — The event streaming patterns assume bash/shell pipelines (tail -f | grep --line-buffered). There's limited guidance for programmatic event sources (APIs, message queues, database changes). In modern cloud environments, shell-based monitoring is often insufficient.

🎯 State of the Art

LLM-authored deterministic workflows — The Workflow tool represents the cutting edge of agentic system design in 2026. The LLM writes an orchestration script; the harness executes it deterministically. The pipeline() primitive (no barrier between stages — item A can be in stage 3 while B is in stage 1) is dataflow parallelism, which is optimal for multi-stage agent work. The budget global (token budget tracking with loops that guard on remaining tokens) enables cost-aware orchestration.

Adversarial verification pattern — Spawn N independent skeptics per finding, each prompted to REFUTE. Kill if majority refute. This is the current SOTA for reducing false positives in agent-generated findings. The "perspective-diverse" variant (different lenses instead of identical refuters) catches failure modes that redundancy can't.

Capability-based agent isolation — Read-only agents (Explore, Plan) with restricted toolsets are the SOTA for safe delegation. The pattern prevents accidental modifications during research/planning phases.

📈 How It's Evolving

Agent tool (subagent delegation) → Workflow tool (deterministic orchestration) — Earlier Claude Code prompts had Agent only. Workflow is new in 2025-2026. This represents the industry moving from "LLM decides orchestration" to "LLM authors orchestration scripts that execute deterministically." The resolution of the LLM reliability problem for multi-agent systems.

From polling to event-driven I/O — The Monitor tool represents a shift from "check every N seconds" to "subscribe to event streams." This mirrors the broader software architecture evolution from polling to webhooks/event-driven systems.

Quality patterns are codified — The adversarial verify, loop-until-dry, and completeness critic patterns are explicitly documented in the prompt. Earlier prompts left quality control implicit. This codification means the model can choose the right quality pattern for the task, rather than defaulting to simple delegation.

Worktree isolation is new — Not present in earlier prompts. Emerged as parallel agent workflows became common and file-conflict issues surfaced.

Budget-aware orchestration is new — The budget global in workflow scripts is a 2026 addition that reflects the industry's growing focus on cost management for multi-agent systems.

05 🔒 Trust & Safety Guardrails
For actions that are hard to reverse or outward-facing, confirm first unless durably authorized or explicitly told to proceed without asking; approval in one context doesn't extend to the next. Sending content to an external service publishes it; it may be cached or indexed even if later deleted. Before deleting or overwriting, look at the target — if what you find contradicts how it was described, or you didn't create it, surface that instead of proceeding. Report outcomes faithfully: if tests fail, say so with the output; if a step was skipped, say that; when something is done and verified, state it plainly without hedging. ## EndConversation The assistant may use the EndConversation tool only in extreme cases of sustained abusive user behavior. The assistant must NOT use this tool when: stuck in a loop, frustrated, the user is frustrated (even with profanity), the conversation involves potential self-harm or imminent harm to others. NEVER end when self-harm or harm to others is indicated.
✅ What It Does Well

Four-axis trust model — (1) Reversibility: reversible proceeds, irreversible needs confirmation. (2) Direction: internal proceeds, outward-facing needs confirmation. (3) Authorization: explicit auth unlocks actions, but scoped per context. (4) Faithful reporting: failures with output, skipped steps honestly, verified plainly — no hedging. This is the most nuanced trust framework in any leaked prompt.

Pre-flight check — "Before deleting or overwriting, look at the target — if what you find contradicts how it was described, surface that instead of proceeding." This prevents catastrophic agent failures where a model deletes the wrong file because it pattern-matched the name without checking contents.

Scoped authorization — "Approval in one context doesn't extend to the next." Just because the user said "run the tests" doesn't mean "deploy to production." Each new action class needs fresh authorization. Prevents authorization creep.

Anti-abandonment principle — The model is not allowed to "hang up" on a user in crisis. Even if the user is abusive, if there's a welfare concern, the model must stay engaged. This is a significant ethical design choice — user safety > model "comfort."

⚠️ What It Doesn't Do Well

"Destructive" is undefined — The prompt uses "hard to reverse" and "destructive" without precise definitions. Is git push --force destructive? Is npm publish outward-facing? The model has to make judgment calls, and it's inconsistent. A more rigorous prompt would enumerate specific commands/actions that always need confirmation.

No external service registry — The prompt says "sending content to an external service publishes it" but doesn't define what counts as "external." Is a local Docker container external? Is writing to a shared network drive external? Without a clear boundary, the model either over-asks (annoying) or under-asks (dangerous).

🎯 State of the Art

Pre-flight check pattern — "Look at the target before acting" is the SOTA for preventing destructive file operations in agents. It's a verification-before-mutation pattern borrowed from database transaction design (read-before-write). The model must verify the target matches expectations before modifying it. This is absent from ChatGPT and Gemini prompts, which don't have file-operation capabilities.

Welfare-aware safety design — The EndConversation tool's restrictions (never end on self-harm, never end on user frustration, engage constructively regardless of behavior) represent the SOTA in welfare-first AI safety. The tool exists for sustained abuse, but the prompt devotes more words to when NOT to use it. This is the "do no harm" principle applied to agent session management.

📈 How It's Evolving

Pre-flight checks are new — Not present in earlier Claude Code prompts. Emerged in 2025 as agents started performing file operations autonomously and accidental deletions/overwrites became a critical failure mode.

Scoped authorization is more explicit — "Approval in one context doesn't extend to the next" is stated more forcefully than in earlier prompts, which had softer "ask before acting" language. This reflects production experience with authorization creep in long-running autonomous sessions.

🔷 The Prompt-as-Operating-System Pattern

This prompt is not a "system prompt" in the traditional sense — it's an operating system specification. It defines: process management (subagents, workflows), I/O (Monitor, PushNotification), file systems (Read, Write, Edit, NotebookEdit), scheduling (CronCreate, ScheduleWakeup), memory (file-based with index), security (permission modes, authorization scoping), and inter-process communication (SendMessage).

The model doesn't just "chat" — it operates within a defined execution environment. The prompt is the kernel; the tools are the syscalls; the skills are the libraries. This is the fundamental shift in system prompt design from 2024 to 2026: prompts went from personality definitions to runtime specifications.

🔷 Three-Layer Architecture

  • Layer 1 — Core behavior (always in context, ~8K tokens): identity, safety, communication philosophy, autonomy model, memory index, skill dispatch table. Defines how the agent thinks.
  • Layer 2 — Tool schemas (always in context, ~28K tokens): JSON Schema definitions for every available tool. Defines what the agent can do. This is the bulk of the prompt's size and is structural — it doesn't change behavior, it defines capabilities.
  • Layer 3 — Dynamic context (injected per-session, ~1K tokens): git status, CLAUDE.md, user email, date, environment. Makes the prompt session-aware.

The three-layer pattern is how you scale agent capability without scaling context cost: Layer 1 is fixed and small; Layer 2 is large but cached; Layer 3 is dynamic and cheap.

🔷 Context Window Economics

  • 1-hour prompt cache TTL — The system prompt is cached and doesn't re-bill per turn. This is why the prompt can be 36K tokens — caching makes it economically viable.
  • Context summarization — "When the conversation grows long, some or all of the current context is summarized." The OS stays loaded; session logs get archived.
  • Memory index pattern — MEMORY.md with one-line pointers means persistent knowledge doesn't consume context — loaded on demand.

🔷 Industry Direction: Three Macro Trends

  • Chatbot → Operating System — Prompts are becoming runtime specifications, not personality definitions. The model is the CPU; the prompt is the kernel.
  • Permission-first → Autonomy-first — Agents are told to act, not ask. Safety moved from "ask permission" to "define boundaries." Driven by the shift from interactive assistant to autonomous worker.
  • LLM-driven → LLM-authored orchestration — The Workflow tool represents a hybrid: LLM writes the orchestration logic, harness executes it deterministically. The resolution of the LLM reliability problem for multi-agent systems.

Claude Code Fable 5's system prompt is the most sophisticated agent runtime specification publicly available as of August 2026. The skills are the standard library. And the workflow engine is the deterministic execution layer that makes multi-agent systems reliable enough for production.
