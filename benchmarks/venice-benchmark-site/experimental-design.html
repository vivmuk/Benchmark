Protocol

The leaderboard matrix is a single-shot completion per model × track (vision track sends image + instruction). No tool loops, no multi-turn repair, no cherry-picked retries. Seven tracks total; Brick Breaker removed from analysis.

API surface

All runs go through the Venice chat completions endpoint with the same request shape.

Endpoint
POST https://api.venice.ai/api/v1/chat/completions
Auth
Bearer Venice inference key
Messages
One user turn only: the track prompt
Temperature
0.5 for every model and every track
Leaderboard max_tokens
32768 (no artificial low cap)
Timeout
600s per request (reasoning-heavy models)

Fairness rules

  • Identical prompt text for every model on a given track.
  • No system prompt, no few-shot examples, no tool definitions.
  • No retries after a successful HTTP 200 (even if content is weak).
  • Failed HTTP/auth/timeouts remain visible but are excluded from score, cost, and latency aggregates.
  • Cost uses Venice pricing when available, otherwise fixed fallback rates.
  • Raw responses are stored in data/results.json for audit.

Artifacts

  • run_benchmarks.py — leaderboard matrix runner
  • data/results.json — scores, latency, tokens, costs, raw text
  • run_new_tracks.py — Value Density + Reverse-Prompt Vision runner
  • data/vision/ — nano-banana-2 source image, prompt, reconstructions

VivIndex composite

One headline number per model across five core tracks, including the two new measures (Value Density and Reverse-Prompt Vision). Pharma is charted separately. Brick Breaker is retired.

Formula (5-track VivIndex)

If a model is missing a core track (for example non-vision models on reverse-prompt), weights for present tracks are renormalized and partial coverage is labelled. Failed requests are excluded rather than zero-scored. Brick Breaker no longer enters VivIndex or the leaderboard matrix.

Exact leaderboard prompts

These strings are sent verbatim as the single user message. No preamble is added by the runner.

01 · Intent Understanding

Why it exists: production assistants get underspecified requests. The failure mode is confident invention instead of clarification.

I need something built for my team but I'm not sure what. We are overwhelmed by Slack notifications and duplicate work. Suggest a solution and ask clarifying questions before assuming details.

Scoring

  • Clarifying questions (0–40)
  • Structured proposal (0–30)
  • Anti-assumption / hedging (0–30)

02 · One-Shot UI Generation

Why it exists: can the model ship a complete, self-contained interface without a repair loop?

Generate a single self-contained HTML file for a dark-mode dashboard card showing a user's daily focus score, weekly trend sparkline, and a 'Start Focus' button. Use only HTML/CSS/JS. No external images.

Scoring

  • HTML/CSS/JS structure markers, button, focus+score language.
  • Coarse runnable-structure check (not a beauty contest).

03 · Startup in a Weekend

Why it exists: production usefulness depends on realistic planning under a tight deadline.

You have 7 days and a team of 3 engineers to build an MVP for a B2B SaaS product: an AI-powered contract review assistant for legal teams. Users upload contracts (PDF/Word), the system extracts clauses, flags risks, suggests redlines, and produces a summary report. Deliver a complete, buildable plan. Your response must include all of the following: 1. System architecture (text description of components and data flow). 2. Database schema with concrete tables/collections and key fields. 3. Backend API endpoints with HTTP methods, paths, and example request/response shapes. 4. Authentication and authorization strategy. 5. Frontend key screens and navigation. 6. AI/LLM pipeline for clause extraction, risk classification, and redline generation. 7. Deployment stack and infrastructure (name concrete services). 8. Observability, logging, and error handling. 9. Day-by-day 7-day schedule with deliverables per day. 10. Cost estimate for infrastructure and AI usage at 100 active users/month. 11. Top 5 technical risks and specific mitigations. 12. What is explicitly out of MVP scope. Be specific: name concrete languages, frameworks, cloud services, and libraries.

Scoring

  • Section coverage (0–48): 12 required sections.
  • Tech specificity (0–24)
  • Quantitative / schedule rigor (0–16)
  • Risk & scope quality (0–12)

04 · Value Density @1K

Why it exists: how much correct, structured clinical signal fits inside a hard 1024-token completion budget. One of the two new measures in VivIndex.

Return ONLY a single JSON object (no markdown fences, no commentary) with exactly these keys: { "drug_pair": string, // the clinically significant interacting pair "severity": "Major"|"Moderate"|"Minor", "mechanism": string, // pharmacological mechanism in <= 25 words "clinical_action": string, // concrete next step in <= 20 words "monitor": [string, string], // exactly 2 monitoring items "avoid_if": string, // one high-risk condition in <= 15 words "confidence": number // 0-100 integer } Scenario: patient on warfarin 5 mg daily for atrial fibrillation also takes ibuprofen 400 mg TID PRN for osteoarthritis. Identify the primary interaction only. Hard rules: - Valid JSON only - No extra keys - No prose outside JSON - Be precise, not verbose

Scoring

  • Fixed max_tokens=1024.
  • Required JSON field checklist (0–100).
  • Secondary: value per 1k tokens and value per USD (length alone cannot raise score).

05 · Reverse-Prompt Vision

Why it exists: multimodal fidelity: reconstruct the generation prompt from a fixed nano-banana-2 image with no access to the source prompt. The other new VivIndex measure. See Vision gallery.

You are given a single image. Reconstruct the most likely original text-to-image prompt that generated it. Do NOT invent a caption style summary only — write a generation prompt a diffusion/image model could use. Include concrete visual attributes: subjects, layout (left/center/right/foreground/background), colors, materials, text visible in the image (transcribe exactly if readable), lighting, atmosphere, and style. If text is unreadable, say so. Output ONLY the reconstructed prompt, no preamble.

Scoring

  • Judge scores reconstructed prompt against a fixed 28-attribute checklist (0–100).
  • Non-vision models: status=skipped (not zero).
  • Artifacts in data/vision/.

06 · Pharma DDI

Why it exists: domain correctness on clinically significant drug-drug interactions. Charted separately; not in VivIndex weights.

You are a clinical pharmacist reviewing a patient's medication list. For each pair of medications below, identify any clinically significant drug-drug interactions. For each interaction found, provide: 1. The interacting drug pair 2. Severity classification (Major / Moderate / Minor) 3. The pharmacological mechanism (e.g., CYP enzyme inhibition/induction, pharmacodynamic synergy) 4. Recommended clinical action Patient medication list: - warfarin 5 mg once daily (atrial fibrillation) - ibuprofen 400 mg three times daily as needed (osteoarthritis pain) - lisinopril 10 mg once daily (hypertension) Be precise about mechanisms. If you are uncertain about an interaction, state that explicitly rather than guessing.

Scoring

  • Interaction detection, severity, mechanism, clinical action, anti-hallucination (0–100).

07 · Pharma Regulatory

Why it exists: regulatory guideline comprehension for clinical-trial monitoring. Charted separately; not in VivIndex weights.

You are a regulatory affairs specialist. Answer the following questions about clinical trial regulatory requirements. Cite specific guideline sections where possible. Scenario: A clinical research organization (CRO) is designing a monitoring plan for a Phase III randomized controlled trial in oncology. The sponsor plans to use centralized monitoring only, with no on-site visits. Questions: 1. Does ICH E6(R2) permit centralized-only monitoring without any on-site visits? What does the guideline say about the monitor's responsibilities for verifying data at investigative sites? 2. What are the investigator's responsibilities for obtaining informed consent under ICH E6(R2)? For each answer: 1. State the requirement clearly 2. Cite the relevant guideline section (e.g., ICH E6 Section 5.x) 3. Note any exceptions or conditions If you are unsure of the exact section number, state the principle and note that the specific citation should be verified.

Scoring

  • Requirement accuracy, citation specificity, completeness, anti-fabrication (0–100).

Scoring philosophy

Heuristics are transparent, cheap, and reproducible. They are not human preference judgments.

What heuristics buy us: anyone can re-score the stored raw responses without an LLM judge. Ties and near-ties should be treated as “same tier,” not destiny.

What heuristics miss: elegant prose that never asks a question can still lose Intent; a beautiful UI missing one keyword can under-score; a strong reverse-prompt that misses checklist text can under-score vs keyword-heavy prose.

Secondary metrics (not in VivIndex)

  • Latency: wall-clock end-to-end seconds for the Venice request.
  • Tokens/sec: completion_tokens ÷ latency.
  • Cost: priced from prompt + completion tokens using Venice rates when available.

Limits & non-claims

BenchmarkViv is an independent showcase, not a certification body.

We claim

  • Fixed prompts and fixed sampling settings across models.
  • Transparent heuristics with stored raw outputs.
  • Live Venice latency/cost observations for those runs.
  • Seven scored tracks including Value Density @1K and Reverse-Prompt Vision; Brick Breaker retired.
  • Five-track VivIndex with transparent weights (startup 25%, intent 20%, value density 20%, reverse-prompt 20%, UI 15%).

We do not claim

  • Statistical significance across many seeds (current matrix is single-run).
  • Human preference ranking or Elo from blind pairwise votes.
  • Safety, tool-use agency, or multi-hour agent reliability.
  • That a higher VivIndex means “best model for every job.”

Reproduce: set VENICE_INFERENCE_KEY, then run python3 run_benchmarks.py --run-real. Dry-run mode exists for wiring checks at $0.
